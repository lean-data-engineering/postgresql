# PostgreSQL Temporal Types 

---

## 1. `DATE`

Stores calendar date only. No time, no timezone.

```sql
SELECT '2024-03-15'::DATE;
SELECT CURRENT_DATE;
```

- **Storage:** 4 bytes
- **Range:** 4713 BC → 5874897 AD
- **Format:** `YYYY-MM-DD`

---

## 2. `TIME` / `TIME WITHOUT TIME ZONE`

Stores time of day only. No date, no timezone.

```sql
SELECT '14:30:00'::TIME;
SELECT '14:30:00.123456'::TIME;   -- microsecond precision
SELECT CURRENT_TIME::TIME;        -- strips timezone from CURRENT_TIME
```

- **Storage:** 8 bytes
- **Range:** `00:00:00` → `24:00:00`
- **Precision:** up to 6 decimal places (microseconds)

```sql
-- precision can be specified
CREATE TABLE shifts (
    start_time TIME(0),   -- no fractional seconds
    end_time   TIME(3)    -- millisecond precision
);
```

---

## 3. `TIMETZ` / `TIME WITH TIME ZONE`

Stores time of day **with** timezone offset. No date.

```sql
SELECT '14:30:00+05:30'::TIMETZ;   -- IST
SELECT '14:30:00-08:00'::TIMETZ;   -- PST
SELECT CURRENT_TIME;                -- returns TIMETZ
```

- **Storage:** 12 bytes
- **Range:** `00:00:00+1559` → `24:00:00-1559`

> ⚠️ **Postgres and the SQL standard both consider `TIMETZ` poorly designed.** A time-of-day with a timezone offset but no date is ambiguous — DST rules depend on the date. The Postgres docs explicitly recommend **avoiding `TIMETZ`** in most cases. Use `TIMESTAMPTZ` instead.

---

## 4. `TIMESTAMP` / `TIMESTAMP WITHOUT TIME ZONE`

Stores date **and** time together. No timezone awareness.

```sql
SELECT '2024-03-15 14:30:00'::TIMESTAMP;
SELECT '2024-03-15T14:30:00'::TIMESTAMP;       -- ISO 8601 format
SELECT '2024-03-15 14:30:00.123456'::TIMESTAMP; -- microseconds
SELECT NOW()::TIMESTAMP;                         -- strips tz info
SELECT CURRENT_TIMESTAMP::TIMESTAMP;
LOCALTIMESTAMP;                                  -- same thing, standard syntax
```

- **Storage:** 8 bytes
- **Range:** `4713 BC` → `294276 AD`
- **What it means:** a "wall clock" reading — literally what the clock on the wall showed, with no information about *where* in the world

```sql
-- typical use: storing local times where timezone is implied/irrelevant
CREATE TABLE local_events (
    event_name TEXT,
    event_at   TIMESTAMP    -- assumes everyone reading this knows the timezone
);
```

---

## 5. `TIMESTAMPTZ` / `TIMESTAMP WITH TIME ZONE`

Stores date and time, **timezone-aware**. This is the most commonly recommended type.

```sql
SELECT '2024-03-15 14:30:00+05:30'::TIMESTAMPTZ;
SELECT '2024-03-15 14:30:00 IST'::TIMESTAMPTZ;
SELECT NOW();               -- returns TIMESTAMPTZ
SELECT CURRENT_TIMESTAMP;   -- returns TIMESTAMPTZ
```

- **Storage:** 8 bytes (same as TIMESTAMP — no extra cost)
- **Range:** `4713 BC` → `294276 AD`

**Critical detail — Postgres does NOT store the input timezone.** It converts everything to **UTC internally**, then converts back to your session timezone on output:

```sql
SET timezone = 'America/New_York';
SELECT '2024-03-15 14:30:00+05:30'::TIMESTAMPTZ;
-- output: 2024-03-15 05:00:00-04  (converted to NY time)

SET timezone = 'Asia/Kolkata';
SELECT '2024-03-15 14:30:00+05:30'::TIMESTAMPTZ;
-- output: 2024-03-15 14:30:00+05:30  (same instant, shown in IST)
```

Both outputs represent the **exact same moment in time** — just displayed differently based on session timezone.

```sql
-- change session timezone
SET timezone = 'Asia/Kolkata';
SET timezone = 'UTC';
SET timezone = 'America/New_York';

SHOW timezone;   -- see current setting
```

## 6. `INTERVAL`

Stores a **duration or span of time**, not a point in time.

```sql
SELECT INTERVAL '3 years 2 months 15 days';
SELECT INTERVAL '8 hours 30 minutes';
SELECT INTERVAL '1.5 hours';
SELECT INTERVAL '90 minutes';
SELECT INTERVAL '-2 days';    -- negative interval
```

- **Storage:** 16 bytes
- **Range:** roughly ±178,000,000 years

### Interval fields and precision

```sql
-- you can restrict what fields are stored
SELECT INTERVAL '3 years 2 months' YEAR TO MONTH;  -- ignores days/time
SELECT INTERVAL '02:30:00' HOUR TO SECOND;
```

### Interval arithmetic

```sql
-- date + interval = date or timestamp
SELECT '2024-01-01'::DATE     + INTERVAL '3 months';    -- 2024-04-01
SELECT '2024-01-01'::TIMESTAMP + INTERVAL '2 hours';    -- 2024-01-01 02:00:00
SELECT NOW()                  + INTERVAL '7 days';      -- one week from now
SELECT NOW()                  - INTERVAL '1 year';      -- one year ago

-- timestamp - timestamp = interval
SELECT '2024-12-31'::TIMESTAMP - '2024-01-01'::TIMESTAMP;
-- 365 days 00:00:00

-- date - date = integer (days), NOT interval
SELECT '2024-12-31'::DATE - '2024-01-01'::DATE;   -- 365 (integer)
```

### Interval input formats

```sql
SELECT INTERVAL '1 year 2 months 3 days 4 hours 5 minutes 6 seconds';
SELECT INTERVAL 'P1Y2M3DT4H5M6S';   -- ISO 8601 duration format
SELECT INTERVAL '01:30:00';          -- hh:mm:ss
```

## Comparison Table

| Type | Date | Time | TZ Aware | Storage | Use When |
|---|---|---|---|---|---|
| `DATE` | ✅ | ❌ | ❌ | 4 bytes | Birthdays, deadlines, calendar dates |
| `TIME` | ❌ | ✅ | ❌ | 8 bytes | Daily schedules, opening hours |
| `TIMETZ` | ❌ | ✅ | ✅ | 12 bytes | ⚠️ Avoid — use TIMESTAMPTZ |
| `TIMESTAMP` | ✅ | ✅ | ❌ | 8 bytes | Local/relative times, logs without tz |
| `TIMESTAMPTZ` | ✅ | ✅ | ✅ | 8 bytes | **Most cases — events, logs, audits** |
| `INTERVAL` | — | — | — | 16 bytes | Durations, time math, expiry windows |

---

## The Golden Rule

```
If in doubt → use TIMESTAMPTZ
```

- It's the same storage cost as TIMESTAMP
- You never lose timezone context
- Postgres handles DST and UTC conversion for you
- Works correctly across servers in different regions

The only time to prefer `TIMESTAMP` is when timezone is genuinely meaningless for your data — e.g. a hypothetical future calendar event where the local wall clock time matters more than the absolute UTC moment.
